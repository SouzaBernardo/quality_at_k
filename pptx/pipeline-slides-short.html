Original paper

Evaluating complete classes

ClassEval evaluates Python classes with interdependent methods.

The benchmark

100 tasks. Each task includes a specification, a test suite, and a human-written reference implementation.

Research question

Correct isolated functions do not guarantee that an entire class works. The paper compares 11 models and three generation strategies.

The evaluation considers both individual methods and the class as a whole.

Du et al. (2023), ClassEval, introduction and Section 3.

Original paper

The correctness criterion

At the method level

A method must pass all of its tests. Tests check return values and changes to object attributes.

At the class level

The class must pass all method and class tests, including interactions between operations.

Vending machine: insert a coin, buy a product, and check the balance and inventory.

Under the original criterion, a solution that passes 99 out of 100 tests still fails.

Du et al., ClassEval, version 2 (2023), Sections 3.2.3 and 4.4, Fig. 4.

Pass@k

The meaning and calculation of Pass@k

Estimated chance of obtaining at least one correct solution among k candidates.

Pass@k=meantasks[1−(n−ck)(nk)]

n · samples

Total solutions generated for the task.

c · correct

Solutions that pass all required tests.

k · candidates

Number of candidates considered in the evaluation, with k ≤ n.

For k = 1, the per-task value is c / n. The values are then averaged across tasks.

Du et al. (2023), ClassEval, Section 4.4. The paper reuses the estimator from Chen et al. (2021).

Our proposal

Pipeline pass_val

StatusP(t) = pass_val
Success1.0 for a class that passes.
PartialSuccessFraction of methods that pass.
Fail or error0.0.

Example: for PartialSuccess, 3 of 4 methods passing gives P(t) = 0.75.

The original class-level Pass@1 requires all tests to pass. Our pass_val allows partial credit.

Local implementation: scripts/take_solution.py, get_task_status(). The fraction of passing methods does not guarantee class integration.

Our proposal

The implemented Quality@1 formula

Quality@1(t) = P(t) × [1 − min(1, β × D(t) / L(t))]
P(t)
pass_val: the task's functional score.
D(t)
sqale_index: estimated technical debt, in minutes.
L(t)
ncloc: non-commented lines of code.
β = 0.1
Penalty weight configured in the code.

Quality adjusts the functional score. When P(t) = 0, the result is also 0.

scripts/compute_fqs.py. D/L is measured in minutes per line. β sets the penalty scale; it is not a universal quality threshold.

Interpretation

What Quality@1 represents

A functional score adjusted by the code's estimated technical debt.

Contribution

Add a maintainability dimension to functional evaluation. With the same pass_val and code size, lower debt yields a higher Quality@1.

Interpretation limits

Partial credit does not prove a class is correct. β controls the penalty and needs validation. A score of 0.95 does not automatically mean a 95% probability of success.

Pass@k evaluates whether accepted solutions can be obtained. Quality@1 combines a functional score with a static code metric.

Du et al. (2023), ClassEval · SonarSource, metric definitions. Proposal: scripts/compute_fqs.py.
