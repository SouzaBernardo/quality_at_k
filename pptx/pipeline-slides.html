Original paper

Generating complete classes

ClassEval: A Manually-Crafted Benchmark for Evaluating LLMs on Class-level Code Generation

Research question

Benchmarks of isolated functions leave open how models generate methods that share state and depend on one another.

Paper contribution

A manually curated Python class benchmark and a study of 11 models comparing three generation strategies.

The evaluated unit includes both the methods and how they work together as a class.

Original paper

Generation strategies

Holistic

The model receives the skeleton and implements the entire class in one generation.

Incremental

The model generates one method at a time, using previously generated method bodies as context.

Compositional

The model generates each method independently, using the signatures of the others. The methods are then assembled into a class.

In the study, GPT-4 and GPT-3.5 performed best with the Holistic strategy. Other models benefited from method-level generation.

Du et al., ClassEval, version 2 (2023), Sections 4.2 and 5.2. Our implementation uses the Holistic strategy.

Original paper

The correctness criterion

At the method level

A method must pass all of its tests. Tests check return values and changes to object attributes.

At the class level

The class must pass all method and class tests, including interactions between operations.

Vending machine: insert a coin, buy a product, and check the balance and inventory.

Under the original criterion, a solution that passes 99 out of 100 tests still fails.

Du et al., ClassEval, version 2 (2023), Sections 3.2.3 and 4.4, Fig. 4.

Pass@k

The components of Pass@k

ComponentMeaning
TaskProgramming problem defined by the benchmark.
nTotal solutions generated for the task.
cNumber of solutions that pass all required tests.
kNumber of candidates considered in the evaluation, with 1 ≤ k ≤ n.

Tests determine c. Complexity and technical debt are not part of this calculation.

Du et al., ClassEval, version 2 (2023), Section 4.4, Eq. 1. The paper reuses Pass@k from Chen et al. (2021).

Pass@k

The estimator formula

Pass@k=meantasks[1−(n−ck)(nk)]

Inside the brackets

Chance that a group of k candidates includes at least one correct solution. The fraction counts groups made up only of incorrect solutions.

Across tasks

The mean combines each task's estimate. For k = 1, the value for each task reduces to c / n.

In the paper: n = 5 and k ∈ {1, 3, 5}. Greedy evaluation uses one solution per task.

Du et al., ClassEval, version 2 (2023), Sections 4.4–4.5. The combinations are sampled without replacement from the n candidates.

Transition to our proposal

Quality of code that passes the tests

Functional evidence

Pass@k checks whether solutions pass the test suite. The paper also introduces DEP to compare method and attribute dependencies with the reference.

Additional dimension

Passing code may still have technical debt and control flow that is hard to understand. Our proposal adds static analysis to functional evaluation.

How much of the functional score remains after accounting for the code's technical debt?

Du et al., ClassEval, version 2 (2023), Section 4.4. DEP is a metric separate from Pass@k. Static quality: SonarSource, metric definitions.

Our proposal

The implemented Quality@1 formula

Quality@1(t) = P(t) × [1 − min(1, β × D(t) / L(t))]
P(t)
pass_val: the task's functional score.
D(t)
sqale_index: estimated technical debt, in minutes.
L(t)
ncloc: non-commented lines of code.
β = 0.1
Penalty weight configured in the code.

Quality adjusts the functional score. When P(t) = 0, the result is also 0.

scripts/compute_fqs.py. D/L is measured in minutes per line. β sets the penalty scale; it is not a universal quality threshold.

Discussion

Choices for validating the proposal

Functional comparability

Report binary pass rates and partial credit separately. Confirm that the analyzed code matches the tested solution after sanitization.

Choosing β

Evaluate sensitivity to the weight. D/L may favor longer code, so examine the effect of normalization.

Missing data

Distinguish a missing measure from zero debt. The current code replaces missing SQALE with 0 and assigns a score of 0 when NCLOC is 0 during the join.

Aggregation

Show counts and means by status. A mean computed only over successful cases does not represent all tasks.

Methodological considerations based on the current implementation. scripts/merge_sonar_metrics.py and scripts/aggregate_results.py.

Discussion

A future extension: Quality@k

The current pipeline calculates Quality@1 per task. An evaluation with k candidates requires a new criterion.

Acceptance criterion

Count in c only solutions that pass all tests and meet a quality threshold. The estimator would then measure the chance of obtaining at least one accepted solution.

Continuous score

Evaluate candidate quality and define how to aggregate it. This choice produces a different score that needs its own definition and validation.

The definition of Quality@k depends on what makes a candidate successful.

Conceptual options for discussion. These extensions are not part of the implemented formula or pipeline.
